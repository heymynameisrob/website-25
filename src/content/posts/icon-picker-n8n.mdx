n8n uses icons and emojis to help people identify projects, workflows and AI agents. The `N8nIconPicker` design system component provides one place to search, preview and select them.

The picker already supported Lucide icons, emojis, colour choices and skin tones. However, after using it a lot, a few problems surfaced. The popover was cramped. It didn't support any key events, so navigating quickly was impossible. It was also over-complex and hard to maintain.

I worked on improving its layout, performance and keyboard support. This post covers three parts of that work: replacing broken virtualisation with progressive rendering, adding X/Y key navigation, and managing performance for thousands of DOM nodes.

You can see the code that shipped for this refactor [here](https://github.com/n8n-io/n8n/pull/35878)

## How it works

The picker is a controlled Vue component. I accepts either an `icon` or `emoji` via the `v-model`. The selected value is shown in the button as the trigger.

When the popover opens, the selected value decides which tab to show. If there is no value, consumers can choose a default tab. This makes the component fit different contexts without adding separate icon-only and emoji-only pickers.

```ts title="IconPicker.vue"
type IconOrEmoji =
  | { type: "icon"; value: string; color?: string }
  | { type: "emoji"; value: string };

function getDefaultTab() {
  if (model.value) return model.value.type === "emoji" ? "emojis" : "icons";
  return props.defaultTab;
}
```

The wider popover gives the search field and its related actions one clear row. Colour, skin tone and random selection controls appear only when they apply to the current tab. The pattern is pretty common and can be seen in Notion, Linear, and man other web apps.

## Progressive rendering

The picker can contain more than 1,000 options. In the existing version, these items were loaded when the component was mounted, then managed with a virtualisation wrapper.

Virtualisation is useful when the large list stays open for a long time whilst the user is scrolling. Whilst it seems like the right approach, the picker is often used to find a single item and closed quickly. Also virtualisation prevents mounting all the rows at once, so searching and key events can be easily distrupted.

Additionally the icon and emoji data are loaded even if a user doesn't open the popover. This is wasteful and hogs memory when it's not needed.

Instead a simple 'progressive render' felt simpler. Since there were no plans to dramatically increase the amount of items, a simpler 'progressive render' felt better. Initial data would be loaded when hovering over the trigger.

```ts title="IconPicker.vue"
const INITIAL_ROW_COUNT = 10;
const ROW_BATCH_SIZE = 10;

const renderedRowCount = ref(INITIAL_ROW_COUNT);

const visibleRows = computed(function getVisibleRows() {
  return activeRows.value.slice(0, renderedRowCount.value);
});

function renderNextBatch() {
  if (!popupVisible.value) return;

  renderedRowCount.value = Math.min(
    renderedRowCount.value + ROW_BATCH_SIZE,
    activeRows.value.length
  );

  if (renderedRowCount.value < activeRows.value.length) {
    renderFrame = requestAnimationFrame(renderNextBatch);
  }
}
```

When the popover begins to mount, 10 rows are added initially and then adds ten more rows during each animation frame until the list is complete. To the naked eye, it often looks instant.

This approach keeps the first render small without changing the structure of the grid. Once rendering finishes, every option is present in the document. Search, browser find, scrolling and keyboard movement can then use the same rows and coordinates.

Any work gets cancelled when the component unmounts, preventing queued frames from continuing after the picker closes or its parent is removed.

```ts title="IconPicker.vue"
onBeforeUnmount(function cancelPendingWork() {
  if (renderFrame !== undefined) cancelAnimationFrame(renderFrame);
  if (itemTooltipTimer !== undefined) clearTimeout(itemTooltipTimer);
});
```

## Keyboard navigation

The main method of finding the icon/emoji you want is search. Naturally we auto-focus the user when the popover mounts. Often you may search for `smile` and have multiple options to choose from. Using keys to navigate to the item you like is much faster and natural than jumping back to your mouse. The existing version didn't support any key events.

Whilst keeping the search input focused, the picker tracks an active grid coordinate in Vue state. Arrow keys change that coordinate. `Enter` selects the active option.

```ts title="IconPicker.vue"
function handlePickerKeydown(event: KeyboardEvent) {
  if (event.key === "Enter" && activeCoordinate.value) {
    event.preventDefault();
    selectActiveItem();
    return;
  }

  if (["ArrowUp", "ArrowDown", "ArrowLeft", "ArrowRight"].includes(event.key)) {
    event.preventDefault();
    const nextCoordinate = getAdjacentPickerCoordinate(
      activeRows.value,
      activeCoordinate.value,
      getPickerDirection(event.key)
    );

    if (nextCoordinate) activatePickerItem(nextCoordinate, event.target);
  }
}
```

Rows can include section headings and can end with fewer items than the rows above them.

Including several navigation helpers therefore work with coordinates rather than a flat item index. Vertical movement skips headings and clamps the column to the number of items in the next row.

This is where GPT 5.6 Sol helped a lot. They are fairly simple to write, but agents can work out the correct calculation much quicker than I can.

```ts title="IconPicker.utils.ts"
function getVerticalCoordinate(
  rows: IconPickerVirtualRow[],
  current: PickerCoordinate,
  direction: -1 | 1
): PickerCoordinate | undefined {
  for (
    let rowIndex = current.row + direction;
    rowIndex >= 0 && rowIndex < rows.length;
    rowIndex += direction
  ) {
    const row = rows[rowIndex];
    if (!row) continue;

    const itemCount = getRowItemCount(row);
    if (itemCount > 0) {
      return { row: rowIndex, column: Math.min(current.column, itemCount - 1) };
    }
  }
}
```

The trade-off here is we're faking a focus state on the active icon/emoji. This can easily confuse screen-readers because as far as they are concerned the search input is what is in focus, not the active item.

Using `aria-activedescendant` to identify the active option while retaining focus on the input gives screen-readers a clear indication of which item is active.

```vue title="IconPicker.vue"
<N8nInput
  v-model="searchQuery"
  role="combobox"
  aria-autocomplete="list"
  aria-controls="icon-picker-options"
  :aria-expanded="popupVisible"
/>

<div id="icon-picker-options" role="grid">
  <div role="row">
    <N8nButton
      role="gridcell"
      tabindex="-1"
      :aria-label="humanizeIconName(name)"
    />
  </div>
</div>
```

## Loading data

Icon metadata and emoji data are large enough that loading both on every page would waste work. The component imports each data set only when required.

Hovering over the trigger starts loading icon metadata before a click. Hovering over a tab does the same for that tab's data. In common pointer interactions, the data is ready by the time the popover or tab opens.

```ts title="IconPicker.vue"
async function loadIconData() {
  if (iconsLoaded.value || iconsLoading.value) return;

  iconsLoading.value = true;
  try {
    const module = await import("./lucideIconData");
    lucideData.value = module.lucideIcons;
    iconsLoaded.value = true;
  } finally {
    iconsLoading.value = false;
  }
}
```

The loading functions guard against duplicate imports. Icon and emoji data also load separately, so someone who only uses icons does not pay the cost of the emoji set.

This creates a useful sequence:

1. Prefetch the likely data after pointer intent.
2. Render a small first set of rows when the popover opens.
3. Fill the remaining rows over later animation frames.
4. Keep the full grid available for scrolling and keyboard navigation.

## Custom tooltips

Every option needs a readable name, but mounting more than 1,000 tooltip components would remove some of the performance gained by progressive rendering.

Instead, the picker renders one shared tooltip. Pointer and keyboard events update its label and position for the current option. A short delay prevents a trail of tooltips when the pointer moves across the grid.

```ts title="IconPicker.vue"
function showItemTooltipForElement(target: HTMLElement, label: string) {
  const rect = target.getBoundingClientRect();

  itemTooltip.value = {
    label,
    left: rect.left + rect.width / 2,
    top: rect.top,
  };
}
```

This keeps the option markup small and gives icons and emojis the same naming behaviour. It also makes the readable label available to pointer, keyboard and assistive technology users.

## Future considerations

The new picker opens with useful content at once, supports two-dimensional keyboard movement, and keeps search focused throughout selection. Its wider layout gives each control a clear place, while conditional and lazy loading keep the component suitable for the many parts of n8n that use it.

Other follow-up work could include measuring open-to-interactive time on lower-powered devices and testing the grid with a wider set of screen readers and browser combinations.
